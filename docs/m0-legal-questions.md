사실관계가 틀리면 답도 틀리기 때문이다.

## 1. 사실관계

### 1.1 서비스가 무엇인가

전하지 못한 말을 익명으로 남기는 **텍스트 게시판**이다. 출시 전이고 이용자는 0명이다.

| | |
|---|---|
| 계정 | **없다.** 회원가입도 로그인도 없다 |
| 편지 | 본문 최대 500자. 관계 종류(전 연인·친구·가족·동료·기타)를 하나 고른다 |
| 모드 A (공개) | 누구나 읽는다 |
| 모드 B (잠금) | 작성자가 단서·질문·답을 정한다. 답을 맞힌 사람만 본문을 본다 |
| 전달 | 작성자가 **링크를 직접 공유**한다. 서비스가 수신자에게 먼저 연락하는 기능은 없다 |
| 운영 | 개인 1인 |
| 검색 | 개별 편지 페이지는 검색엔진 색인을 막는다(`noindex`) |

**편지는 본질적으로 제3자에 관한 글이다.** 헤어진 연인, 친구, 가족, 직장 동료에게 하려던
말을 적는 서비스이므로, 본문에 그 사람에 관한 서술이 담긴다. 그 제3자는 서비스 이용자가
아니고 동의한 적이 없다. 이 사실이 [Q4](#q4--제3자에-관한-민감정보-l-006)의 배경이다.

### 1.2 저장하는 데이터 — 전수

데이터베이스 테이블 13개 전부다. 빠뜨린 것이 없도록 스키마 파일에서 그대로 옮겼다.

| 테이블 | 무엇이 들어가나 | 사람에 관한 값 |
|---|---|---|
| `letters` | 편지 본문 · 관계 종류 · 잠금 편지의 단서/질문 · 위험 등급 · 상태 · 시각 | 본문(제3자 서술 가능) · `author_fp_hash` |
| `author_contacts` | **이메일 주소(선택)** · 해지 토큰 · 알림 발송 시각 | **이메일 원문** |
| `email_suppressions` | 알림을 해지한 주소의 `sha256` 해시 · 해지 시각 | 주소 해시 (원문 없음) |
| `unlock_attempts` | 잠금 편지 열람 시도 기록 — 편지 ID · `fp_hash` · 성공 여부 · 시각 | `fp_hash` |
| `unlocks` | 열람 성공 — 편지 ID · `fp_hash` · 수신자 응답(예/아니오/모름) · 시각 | `fp_hash` |
| `reports` | 신고 — 편지 ID · 사유 · `reporter_fp_hash` · 처리 상태 | `fp_hash` |
| `appeals` | 이의 제기 — 편지 ID · **자유 텍스트 메시지** · 처리 상태 | 이용자가 적는 자유 텍스트 |
| `deletion_requests` | 삭제 요청 — **본문 일부 인용** · **회신용 연락처(선택, 원문)** · 처리 상태 | **연락처 원문** · 본문 조각 |
| `reactions` | 고정형 반응 4종 — 편지 ID · 종류 · `fp_hash` | `fp_hash` |
| `filter_events` | 자동 검사 판정 통계 — 등급 · 탐지 항목 · 결과 · 시각. **본문 없음** | 없음 |
| `admin_actions` | 운영자 조치 기록 — 조치명 · 대상 ID · 메모 · 시각 | 없음 |
| `app_settings` | 킬 스위치 두 개(공개 읽기 · 작성) | 없음 |
| `events` | 이용 기록 — 이벤트 이름 · **익명 세션 ID(쿠키)** · 부가값 · 시각 | 익명 세션 ID |

**`fp_hash`가 무엇인가** — 이것이 [Q2-a](#q2--개인정보보호법-일반-l-001)의 핵심이다.

```
fp_hash = HMAC-SHA256(서버 비밀키, normalize(IP 주소) + '|' + User-Agent 문자열)
```

- **원본 IP와 User-Agent는 어디에도 저장하지 않는다.** 위 해시값만 남는다
- 목적은 셋뿐이다: 도배 방지(레이트리밋), 잠금 편지의 시도 횟수 제한, 같은 반응 중복 방지
- 키는 서버만 갖고 있고 언제든 교체할 수 있다. 교체하면 이전 값과의 연결이 끊긴다
- IPv6는 상위 64비트만 쓴다 (단말이 하위 비트를 자주 바꾸기 때문)
- 계정이 없으므로 이 값에서 사람을 특정할 경로가 우리 쪽에 없다

**`events`에 담기지 않도록 코드로 막아둔 것** — 편지 ID · 이메일 · IP · User-Agent. 개발
환경에서는 이 키가 들어오면 예외를 던져 배포 전에 죽는다(`src/lib/events.ts`). 편지 ID를
막는 이유는 `세션 ID ↔ 편지 ID` 연결이 생기는 순간 "누가 어떤 편지를 썼는가"를 조회할 수
있는 표를 우리가 직접 만드는 셈이 되기 때문이다.

### 1.3 저장하지 않는 것

| 항목 | 대신 무엇을 저장하나 |
|---|---|
| 잠금 편지의 답 원문 | HMAC 해시만. 원문은 어디에도 없다 |
| 편지 관리 링크의 토큰 원문 | `sha256` 해시만. 그래서 분실 시 재발급이 불가능하다 |
| **자동 검사가 게시를 막은 편지의 본문** | 아무것도 저장하지 않는다. `filter_events`에 등급·탐지 항목·시각만 남는다 |
| 원본 IP 주소 · User-Agent | 위 `fp_hash`만 |

세 번째 줄이 [Q1-a](#q1--미성년-관련-성적-콘텐츠-처리-l-007)에서 다시 나온다. 게시가
차단된 편지는 **본문이 서버에 한 순간도 남지 않는다.**

### 1.4 보관 기간 — 현재 상태

**자동 파기 절차가 하나도 구현돼 있지 않다.** 이것이 [Q2-b](#q2--개인정보보호법-일반-l-001)다.

| 항목 | 현재 | 비고 |
|---|---|---|
| 편지 | **무기한.** 만료·자동 삭제 없음 | 의도한 설계다 — "공개 감정 아카이브"가 스스로 지워지면 아카이브가 아니라는 판단 |
| 이메일 주소 | 해지 링크 클릭 시 즉시 삭제 · 편지 삭제 시 함께 삭제 | 자동 만료는 없다 |
| `fp_hash` (모든 테이블) | **파기 절차 없음** | 90일을 기본값으로 적어뒀으나 **코드에 파기 작업이 없다** |
| 이용 기록(`events`) | **파기 절차 없음** | 쿠키 자체는 90일 후 만료되지만 **DB의 행은 남는다** |
| 삭제 요청의 연락처 · 본문 조각 | **파기 절차 없음** | 처리 완료 후에도 행이 남는다 |
| 이의 제기 메시지 | **파기 절차 없음** | 처리 완료 후에도 행이 남는다 |

처리방침 초안은 이 상태를 숨기지 않고 그대로 적었다 — "접속 정보로 만든 식별값과 이용
기록은 현재 자동으로 삭제하는 절차가 없습니다."

### 1.5 연령 처리 — 현재 상태

| 지점 | 연령 확인 |
|---|---|
| 편지 작성 · 열람 · 목록 보기 | **없다.** 개인정보를 수집하지 않으므로 |
| 이메일 주소 입력 | **체크박스 1개 필수** — "만 14세 이상입니다". 체크하지 않으면 주소를 저장하지 않는다. 서버에서 강제한다 |
| 약관 | 최소 연령을 명시하되 **검증하지 않는다**고 적었다 |

자기신고식 연령 게이트를 서비스 전체에 두는 방안은 검토했으나 기각했다 — 계정이 없어
확인할 수단이 없고, 절차를 두어도 스스로 적는 값이라 실효가 없다고 판단했다. 이 판단의
법적 타당성이 [Q3](#q3--만-14세-미만-이용자-l-002)다.

### 1.6 편지가 사라지는 경로 셋 — 실제 동작

**셋 다 이른바 soft delete이고, 본문은 데이터베이스에 그대로 남는다.** 이 사실이
[Q1-b](#q1--미성년-관련-성적-콘텐츠-처리-l-007)와 [Q2-c](#q2--개인정보보호법-일반-l-001)
양쪽에 걸린다.

| 경로 | 누가 | 데이터에 실제로 일어나는 일 |
|---|---|---|
| 작성자 삭제 | 작성자가 관리 링크로 직접 | 상태를 `deleted_by_author`로 바꾸고 삭제 시각을 기록. **본문은 남는다.** 등록된 이메일 주소는 같은 트랜잭션에서 실제로 삭제된다 |
| 운영자 조치 | 신고 판정 · 긴급 대응 | 상태를 `hidden_admin`으로. **본문은 남는다.** 이메일 주소도 남는다(비공개 사실을 알려야 하고 이의 제기로 복구될 수 있다) |
| 삭제 요청 | 관리 링크를 잃은 작성자 · 편지에 언급된 당사자 | 운영자가 본문 일부를 대조한 뒤 위 「작성자 삭제」와 같은 처리 |

세 경로 모두에서 **외부 표면(목록·직접 링크·공유 카드)은 즉시 404가 된다.** 남는 것은
데이터베이스 안의 행이다.

### 1.7 처리 위탁 — 넷 다 해외 사업자다

이것이 [Q2-d](#q2--개인정보보호법-일반-l-001)다.

| 위탁처 | 무엇을 맡기나 | 무엇이 넘어가나 |
|---|---|---|
| Vercel | 서비스 호스팅 | 요청 전체 |
| Supabase | 데이터베이스 | §1.2의 전부. **저장 리전은 아직 정하지 않았다** |
| Resend | 알림 메일 발송 | **이메일 주소** |
| OpenAI | 편지의 자동 위험 검사 | **편지 본문 전체** · 잠금 편지의 단서 · 질문 · 답 |

마지막 줄이 [Q4-b](#q4--제3자에-관한-민감정보-l-006)다 — 제3자에 관한 서술이 담긴 본문이
검사를 위해 해외 사업자에게 전달되는데, 그 제3자에게는 동의를 받을 방법이 없다.

심각한 신고가 들어오면 텔레그램 봇으로 운영자에게 알림이 간다. 그 메시지에 담기는 것은
**신고 사유와 편지 ID뿐**이고 이용자의 개인정보는 가지 않아 위탁 표에 넣지 않았다. 다만
"편지 ID가 외부 메신저로 나간다"는 사실 자체를 고지 대상으로 볼지는 [Q2-f](#q2--개인정보보호법-일반-l-001)에서 함께 묻는다.

### 1.8 자동 검사가 무엇을 하는가

편지를 게시하기 전에 두 층으로 검사한다.

1. **층 1 — 정규식과 사전.** 전화번호 · 이메일 · URL · 학교명 · 회사명
2. **층 2 — 언어 모델(OpenAI).** 인명 후보 · 지명과 시기의 조합 · 자해 · 미성년 관련 성적 표현 · 협박

판정은 세 등급이다.

| 등급 | 무슨 일이 일어나나 |
|---|---|
| `low` | 그대로 게시된다 |
| `medium` | 경고 화면을 띄운다. 작성자가 고치거나, 그대로 진행하면 게시되되 **공개 목록에는 뜨지 않는다** (링크를 아는 사람만 본다) |
| `high` | **게시를 막는다. 본문을 저장하지 않는다** |

미성년 관련 성적 표현은 `high`다. 즉 **자동 검사가 잡으면 그 편지는 데이터베이스에 존재한
적이 없다.**

## 2. 질문

각 질문은 "우리가 지금 이렇게 하고 있는데 이것이 맞는가"의 형태로 적었다. 열린 질문보다
검증 가능한 질문이 답을 쓸모 있게 만든다고 보았다.

### Q1 — 미성년 관련 성적 콘텐츠 처리 (L-007)

우리는 이 사안을 임의로 판단하지 않기로 하고, 답이 올 때까지 **편지가 사라지는 모든
경로를 파일 하나(`src/lib/letters/deletion.ts`)에 모아두었다.** 답이 오면 그 파일 하나와
마이그레이션 하나로 반영이 끝나도록 만든 것이다.

경로가 **둘**이고 데이터에 남는 것이 서로 다르다. 답도 다를 수 있다고 보아 나눠 묻는다.

**Q1-a. 사전 차단 — 지금은 본문이 아예 저장되지 않는다.**
자동 검사가 미성년 관련 성적 표현으로 판정하면 게시를 막고 **본문을 저장하지 않는다.**
남는 것은 "이런 등급의 시도가 이 시각에 있었다"는 통계 행 하나뿐이고, 거기에 본문은 없다.

- 이 설계 자체에 문제가 있는가? 즉, **시도된 내용을 보존해야 할 의무**가 있는가?
- 보존 의무가 있다면 무엇을(본문 전체인가 일부인가), 어디에, 얼마나?
- 이 시점에 **신고 의무**가 발생하는가? 게시되지 않았고 작성자를 특정할 정보도 없는데도?

**Q1-b. 사후 발견 — 게시된 뒤 신고로 내렸을 때.**
자동 검사를 통과해 게시된 편지가 신고로 발견되면 운영자가 즉시 비공개 처리한다. 이때
**본문은 데이터베이스에 그대로 남는다**(§1.6).

- **즉시 완전 삭제해야 하는가**, 아니면 **신고·수사 대응을 위해 보존해야 하는가**?
- 보존해야 한다면: **어디에**(운영 DB 안의 별도 격리 영역인가, 분리 보관인가), **어떤
  형태로**(원문인가 암호화인가), **얼마나**, **누가 접근할 수 있어야 하는가**?
- 지금처럼 "운영 DB에 상태만 바꿔 남겨두는 것"은 보존으로 인정되는가, 아니면 그 자체가
  문제인가?

**Q1-c. 신고 의무.**

- 발견 시 수사기관이나 특정 기관에 **신고할 의무**가 있는가?
- 있다면 **무엇을**, **얼마 안에**, **어디로** 신고해야 하는가?
- 1인 운영자가 새벽에 발견했을 때 실제로 따를 수 있는 절차인가?

**Q1-d. 우리가 가진 것이 없다는 사실.**
계정이 없어 작성자를 특정할 정보가 우리에게 없다. 수사기관이 요청해도 실제로 넘길 수
있는 것은 **`fp_hash`(IP와 브라우저 정보의 해시)와 타임스탬프뿐**이고, 원본 IP는 저장하지
않는다.

- 이 상태로 위 의무를 다한 것이 되는가?
- **원본 IP를 저장하도록 설계를 바꿔야 하는 법적 요구가 있는가?** (있다면 지금 바꿔야
  한다. 나중에 바꾸면 그 이전 편지에는 소급되지 않는다)

### Q2 — 개인정보보호법 일반 (L-001)

**Q2-a. `fp_hash`가 개인정보인가.**
§1.2의 산출식대로 만든 값이다. 원본 IP·User-Agent는 저장하지 않고, 키는 서버만 갖고
있으며 교체하면 연결이 끊긴다. 계정이 없어 이 값에서 사람에 도달할 경로가 우리 쪽에 없다.

- 이 값이 **개인정보인가**? 가명정보인가? 아니면 개인정보가 아닌가?
- 답에 따라 보유기간 고지·파기·안전조치 의무의 적용 여부가 달라진다고 이해하고 있는데,
  맞는가?

**Q2-b. 보유기간과 파기 — 파기 절차가 없다.**
§1.4가 현재 상태다. 편지는 무기한 보관이 **의도한 설계**이고, `fp_hash`와 이용 기록에는
파기 작업이 아예 구현돼 있지 않다.

- **편지를 무기한 보관하는 것**이 허용되는가? 허용된다면 고지만 하면 되는가?
- `fp_hash`·이용 기록에 **파기 절차를 두는 것이 의무인가**, 아니면 "삭제하지 않는다"고
  고지하는 것으로 충분한가?
- 의무라면 **90일이 방어 가능한 기간인가?** 우리가 정할 수 있는 값인가, 법이 정하는가?
- `deletion_requests`(연락처 원문 · 본문 조각)와 `appeals`(자유 텍스트)는 처리가 끝난 뒤에도
  남는다. 처리 완료 후 파기 의무가 있는가?

**Q2-c. "삭제"라고 안내하고 본문을 보관하는 것.**
이용자에게는 "편지를 삭제할 수 있습니다"라고 안내하고 실제로 외부 표면에서는 즉시
사라지지만, **데이터베이스 안의 본문은 남는다**(§1.6).

- 이것을 "삭제"라고 안내해도 되는가? 파기 의무 위반인가?
- 안내 문구를 어떻게 고쳐야 하는가? 아니면 실제로 본문을 지우도록 동작을 바꿔야 하는가?
- (Q1-b의 답이 "보존"이면 이 둘이 충돌한다. 그때는 어느 쪽이 우선하는가?)

**Q2-d. 국외 이전.**
위탁 네 곳이 전부 해외 사업자다(§1.7).

- 이것이 **개인정보 국외 이전**에 해당하는가? 해당한다면 고지만 하면 되는가, 별도 동의가
  필요한가?
- 처리방침 초안에는 위탁 목록만 있고 **국외 이전 항목이 없다.** 무엇을 어떤 형식으로
  적어야 하는가?
- **Supabase 리전을 한국으로 정하면 달라지는 것이 있는가?** (아직 정하지 않았으므로 답에
  맞춰 고를 수 있다)

**Q2-e. 개인정보 보호책임자.**
개인 1인이 운영한다. 법인이 없고 사무실 주소도 없다.

- 보호책임자의 **이름과 연락처를 공개해야 하는가**? 개인 실명과 주소까지 올려야 하는가?
- 이메일 주소만으로 충분한가?
- 이 서비스 규모(이용자 0명, 개인 운영)에 적용되지 않는 의무가 있는가?

**Q2-f. 처리방침 초안 검토.**
초안을 인쇄해 함께 가져간다(§부록). **지금 적혀 있는 것은 전부 코드가 실제로 하는
일이고, 확인되지 않은 것은 적지 않았다.**

- **빠진 필수 항목이 무엇인가?** 우리가 비워둔 자리는 이렇다: 보유기간·파기절차, 보호책임자
  연락처, 열람·정정·처리정지 요구 창구, 권익침해 구제 방법, 방침 변경 고지 절차, 시행일
- 약관 쪽에 비워둔 자리: 면책 범위 · 준거법 · 관할 · 분쟁 해결 · 약관 변경 고지 절차 · 시행일
- 심각 신고 시 **편지 ID가 텔레그램으로 나가는 것**을 고지해야 하는가?
- 표현 중 **사실과 다르게 읽힐 위험이 있는 문장**이 있는가?

### Q3 — 만 14세 미만 이용자 (L-002)

**Q3-a. 개인정보를 수집하지 않는 이용에 연령 게이트가 필요한가.**
편지 작성·열람·목록 보기에는 개인정보 수집이 없다(§1.5). 그래서 연령 확인을 두지 않았다.

- 이 판단이 맞는가? **개인정보를 수집하지 않는 서비스 이용 자체**에 연령 확인 의무가
  붙는가?

**Q3-b. 체크박스 하나가 법정대리인 동의를 대체하는가.**
이메일 주소를 받는 시점에만 "만 14세 이상입니다" 체크박스 하나를 필수로 두고, 체크하지
않으면 주소를 저장하지 않는다. 서버에서 강제한다.

- 이 방식이 **만 14세 미만의 개인정보 수집을 막은 것**으로 인정되는가?
- 아니라면 무엇을 더 해야 하는가? **법정대리인 동의 절차를 실제로 구현해야 하는가?**
  (계정이 없는 서비스에서 그것이 가능한 형태인지도 함께 묻고 싶다)

**Q3-c. 미성년자가 쓴 글 자체.**
본문은 개인정보가 아니지만, 미성년자가 자기 이야기를 공개 게시판에 올리는 것이다.

- 여기에 별도의 의무가 붙는가? 사후 삭제 요구권이 다르게 적용되는가?

### Q4 — 제3자에 관한 민감정보 (L-006)

**Q4-a. 플랫폼의 의무 범위.**
편지는 본질적으로 제3자에 관한 글이다(§1.1). 자동 검사는 신상 정보(연락처·URL·학교·회사·
인명 후보)를 잡지만, **건강·성생활·정치성향 같은 민감정보 언급은 별도로 잡지 않는다.**
신고 사유 목록에는 성적 내용 항목이 있다.

- 제3자의 민감정보가 담긴 글이 게시되는 것에 대해 플랫폼이 지는 의무는 무엇인가?
- **사전 차단 의무인가**, 아니면 **신고를 받고 조치하는 것으로 충분한가**?
- 사전 차단 의무라면 어느 범위까지인가? (자동 검사에 항목을 추가해야 한다면 지금 추가한다)

**Q4-b. 본문이 OpenAI로 전달되는 것.**
자동 검사를 위해 **편지 본문 전체**가 OpenAI로 전달된다(§1.7). 본문에는 제3자에 관한
서술이 담기고, **그 제3자에게 동의를 받을 방법이 없다** — 우리는 그가 누구인지 모른다.

- 이것이 문제인가? 작성자의 동의만으로 성립하는가?
- 처리방침에 어떻게 적어야 하는가? (초안에는 "편지 본문과 단서·질문·답이 검사를 위해
  전달됩니다"라고 적었다)
- 검사를 국내에서 수행하거나, 전달 전에 가공해야 할 필요가 있는가?

**Q4-c. 편지에 언급된 당사자의 삭제 요구권.**
제3자가 "내 이야기가 올라와 있다"며 삭제를 요청하는 경우다. 지금 우리가 가진 경로는
**본문 일부를 적어 삭제를 요청하는 폼 하나**이고, 운영자가 본문을 대조한 뒤 처리한다.
판정이 애매하면 삭제하는 쪽으로 정해두었다.

- 제3자에게 **삭제 요구권**이 있는가? 있다면 근거가 무엇인가?
- 본인 확인을 어떻게 해야 하는가? 지금 방식(본문 대조 + 운영자 판단)으로 충분한가?
- **본문 일부만 아는 사람이 남의 편지를 지울 수 있다**는 위험을 우리가 감수하고 있다.
  이 판단이 맞는가, 아니면 더 엄격한 확인이 요구되는가?
- 발신자 정보 제공 요구가 오면 — 우리에게 **실제로 없다**(§Q1-d). 이 사실을 어떻게
  회신해야 하는가?

## 4. 상담 자리에서 확인할 것

1. **답을 문서로 받는다.** 구두로 받았으면 이쪽에서 정리해 보내고 확인을 받는다 — 나중에
   "그렇게 말한 적 없다"가 되면 근거가 없어진다
2. **각 답의 근거 조문을 함께 받는다.** 결정 로그에 옮길 때 인용해야 한다
3. **Q1의 답이 갈리는 조건을 확인한다** — "경우에 따라 다르다"면 그 경우가 무엇인지
4. **재상담이 필요한 시점**을 확인한다 (이용자 규모? 사고 발생 시? 모드 C 착수 시?)
5. 미룬 항목 셋(모드 C 관련 둘, 앱스토어 정책 하나)은 **이번에 묻지 않는다.** 지금 답을
   받아도 착수 시점에 다시 물어야 한다
