# 운영 런북 (v0)

**이 문서는 새벽 2시에 읽는 문서다.** 설명은 다른 문서에 있다. 여기는 절차만 적는다.

---

## 1. 매일 루틴 — 아침 15분 / 저녁 15분

```
1. /admin/queue 연다
2. 자동 비공개 건 → §2 판정표로 처리
3. 이의 제기 → 원 신고와 함께 재검토 → `restore`(되살림) 또는 `reject`
4. 삭제 요청 → §5
5. 심각 카테고리 알림 확인 (신상 / 미성년 / 자해) — 텔레그램 ([발송 §3](./09-notifications.md))
```

**상한은 하루 1시간이다.** 넘기 시작하면 전환 트리거(위협 모델, 비공개)가 발동한 것이다. 더 열심히 하지 말고 §7로 간다.

---

## 2. 신고 판정표

| 신고 사유 | 판정 기준 | 조치 |
|---|---|---|
| **신상 노출** | 연락처 · 주소 · 학교 · 회사 · 실명이 본문이나 단서에 있는가 | **즉시 삭제**. 복구 없음 |
| **저격 · 비방** | 제3자가 그 사람이 누군지 알아볼 수 있는가 + 부정적 내용인가 | 둘 다면 삭제. 하나만이면 복구 |
| **사칭** | 검증 수단이 없다 (무계정) | 신고 2건 이상이면 삭제. 1건은 보류 |
| **성적 내용** | 미성년 관련인가 | 미성년 관련이면 **즉시 삭제 + §4**. 성인 간이면 노골적일 때만 |
| **자해 · 협박** | 압박 도구인가, 실제 위기 신호인가 | **둘 다 삭제.** 위기로 보이면 §4 |
| **스팸 · 광고** | 명백 | 삭제 + `fp_hash` 차단 |
| **기타** | — | 위 항목에 안 걸리면 복구 |

### 큐에는 분류기가 붙여둔 초안이 있다

신고가 접수되면 [분류기](./05-api.md)가 편지를 한 번 더 읽고 **위 표의 어느 행에 걸리는지 · 근거 한 줄 · 신뢰도**를 큐 항목에 붙여둔다. 제출 경로가 아니므로 지연이 무관하고, 운영자는 처음부터 읽는 대신 확인만 하면 된다. 건당 1분이라는 상한이 실제로 지켜지는지가 전환 트리거(위협 모델, 비공개)를 좌우한다.

> **판정은 사람이 한다.** 분류기에 조치까지 맡기면 [D-012](./00-decisions.md)가 "사후에는 사람이 판단한다"를 전제로 사전 검토를 기각한 근거가 조용히 무너지고, 운영자는 승인 버튼만 누르는 사람이 된다.
>
> 그래서 큐는 **후보 행과 근거만** 보여주고 조치 버튼은 비워둔다. 초안 판정과 최종 판정이 어긋난 비율은 §7 주간 점검에서 본다 — 이게 높으면 초안을 믿으면 안 된다는 신호다.

### 판정 원칙 세 개

1. **애매하면 내린다.** 정상 편지 하나가 몇 시간 가려지는 비용 < 문제 편지 하나가 몇 시간 떠 있는 비용.
2. **복구할 때는 `dismiss`를 쓴다** — `auto_hide_exempt`가 세워져 같은 편지가 반복 신고로 계속 내려가는 걸 막는다 ([데이터 모델 §3](./04-data-model.md)). 이의 제기를 받아들여 되살릴 때는 `restore`이고, 효과는 같다.
3. **판정 이유를 `admin_actions.note`에 한 줄 남긴다.** 나중에 같은 유형이 왔을 때 기준이 흔들리지 않는다.

## 3. 킬 스위치

`/admin` → 설정.

| 스위치 | 누가 끄나 | 언제 |
|---|---|---|
| `writing_enabled = false` | 운영자 | 스팸 폭주, 필터 오작동, **자리를 비울 때** |
| `public_read_enabled = false` | 운영자 | 문제 콘텐츠가 여러 건 떠 있고 개별 처리로 못 따라갈 때 |
| `retention_healthy = false` | **파기 잡이 스스로** | 파기가 실패했을 때 ([D-031](./00-decisions.md)) |

**자리를 비울 때는 읽기가 아니라 작성을 끈다.** `public_read_enabled=false`는 피드뿐 아니라 **이미 공유된 링크까지 전부 죽인다** — 그게 사고 대응에는 맞지만 부재 중에 쓰면 유통이 통째로 끊긴다. 작성을 끄면 새 위험만 멈추고 기존 콘텐츠는 계속 돈다.

셋 모두 **관리 화면(`/manage/:token`)은 끄지 않는다.** 사고 대응 중에도 작성자는 자기 편지를 지울 수 있어야 한다.

### 세 번째 스위치는 성격이 다르다

`retention_healthy`가 꺼져 있으면 작성이 막히는데(`writing_enabled`와 같은 응답을 준다), **그냥 켜면 안 된다** — 파기되지 않는 상태에서 데이터가 다시 쌓이기 시작한다.

```
1. Actions 탭에서 「파기 잡」 워크플로의 실패 로그를 본다
2. 원인을 고친다
3. workflow_dispatch로 손으로 한 번 돌린다
4. 성공하면 잡이 스스로 다시 켠다 — 손으로 켜지 않는다
```

4번이 규칙이다. 손으로 켜면 "파기가 되는지 확인하지 않은 채 작성을 다시 받는" 상태가 되고, 그건 스위치가 막으려던 바로 그것이다.

**작성자에게는 세 스위치가 구분되지 않는다.** 응답이 같다 — 왜 꺼졌는지는 운영자가 알아야 하는 정보이지 이용자에게 흘릴 정보가 아니다. 구분은 `app_settings`에 남는다.

## 4. 긴급 대응 (심각 카테고리)

신상 유출 / 미성년 관련 성적 내용 / 실제 위기 신호.

```
1. 해당 편지 즉시 비공개            (1분)
2. 유사 편지 있는지 확인            (5분)
   - 같은 fp_hash의 다른 편지
   - 같은 시간대 유사 패턴
3. 여러 건이면 public_read_enabled = false
4. admin_actions에 기록
5. 24시간 안에 원인 판단:
   필터를 뚫었나 / 필터가 못 잡는 유형인가 / 신고가 늦었나
6. 필터 수정 또는 전환 트리거(위협 모델, 비공개) 검토
```

미성년 관련 성적 내용의 데이터 처리 ([L-007 답](./00-decisions.md)):

| 경로 | 어떻게 |
|---|---|
| 자동 검사가 막은 것 | **원문을 저장하지 않는다.** 차단 원문 보관 테이블을 만들지 않는다 |
| 게시 후 신고로 발견 | 즉시 외부 차단 → **최대 30일 암호화 격리** → 삭제 · 복원 · `legal_hold` 중 하나로 종결 ([D-028](./00-decisions.md)) |
| 작성자가 관리 링크로 지운 것 | 이의 절차 없이 **즉시 완전 파기** ([D-027](./00-decisions.md)) |

**일반적 신고의무는 없다고 본다.** 다만 **특정 아동의 현재 위험 · 진행 중인 성범죄 · 유인·협박 · 즉각적 재범 가능성**이 구체적으로 드러나면 위 1번(즉시 비공개) 직후 **112에 신고한다.** 판단이 서지 않으면 신고하는 쪽으로 기운다 — §2의 "애매하면 내린다"와 같은 계산이다.

> **격리는 자동이다.** 심각 카테고리 신고가 접수되면 비공개와 동시에 본문이 암호화 영역으로 옮겨진다 — 운영자가 할 일이 아니다. 판정 화면은 그 본문을 복호해 보여주고, 격리 시각과 30일 시한을 함께 표시한다.
>
> **30일 종결은 파기 잡이 강제한다** ([D-031](./00-decisions.md) · 매일 새벽 4시). 시한이 지나면 격리 본문이 자동으로 파기된다. 멈추는 경우는 둘뿐이다 — `legal_hold`가 세워져 있거나, 이의 제기가 열려 있거나. 후자는 큐 맨 위에 빨간 상자로 뜬다. 그게 보이면 그 이의 제기를 먼저 판정한다 — 판정하면 다음 회차에 종결된다.
>
> `legal_hold`는 **적법한 영장·법원 명령·구체적 보존 요청이 있을 때만** 세운다. 세우면 시한이 멈춘다. §6의 "공문이나 영장을 확인하기 전에는"과 같은 문턱이다.

실제 위기 신호일 때 우리가 하는 것은 **위기 상담 안내 노출**까지다. 개입하지 않고, 상담자 역할을 하지 않고, 대신 연락하지 않는다 ([D-001](./00-decisions.md)). 노출 지점은 작성 시점의 차단 화면 하나다 ([흐름 1-6-1](./03-flows.md)) — 이미 게시된 편지를 신고로 내릴 때는 작성자에게 도달할 수단이 없다. 이메일을 안 남겼으면 `/manage/:token`뿐이고, 우리가 먼저 연락하지 않는다([D-006](./00-decisions.md)). 여기서 더 하려는 유혹이 생기지만 v0 범위 밖이다.

## 5. 삭제 요청

### 작성자 본인 (관리 링크 있음)

자동 처리. 운영자 개입 없음. `author_contacts` 행도 같은 트랜잭션에서 지우고, 억제 목록에는 넣지 않는다 — 근거는 [발송 §4](./09-notifications.md).

### 관리 링크 분실

```
1. /admin/queue → 삭제 요청
2. body_excerpt를 해당 편지 본문과 대조
3. 일치하면 삭제. 애매하면 삭제 (편지를 지키는 것보다 삭제가 안전)
4. 큐에서 처리 완료로 내린다 — 대조한 편지 ID를 함께 넣는다
   (POST /api/admin/deletion-requests/:id/resolve, [API §4](./05-api.md))
5. contact가 있으면 처리 완료 회신
```

4번이 편지를 `deleted_by_author`로 지우고 요청 행에 `letter_id`를 채운다. 이 단계가 없으면 처리한 요청이 큐에 계속 남아 §1의 15분이 지켜지지 않는다.

### 개인정보 삭제 요청 (이메일)

`author_contacts` 해당 행 삭제. 편지 자체는 별개 — 편지도 지우려면 위 절차. **반대 방향은 자동이다**: 편지를 지우면 이 행도 함께 지워진다(위 「작성자 본인」 · 「관리 링크 분실」 둘 다). 비공개(`hidden_auto`·`hidden_admin`)는 삭제가 아니므로 행이 남는다 — 3번 메일이 바로 그 상태를 알리는 메일이다.

요청자가 **잘못 받은 사람**(자기가 넣은 적 없는 주소)이면 `email_suppressions`에도 넣는다. 행만 지우면 작성자가 같은 주소를 다시 등록할 수 있다 ([발송 §1](./09-notifications.md)).

## 6. 외부 문의

### 수사기관

- **공문이나 영장을 확인하기 전에는 어떤 데이터도 제공하지 않는다.**
- 임의 제공 금지. 요청받은 사실과 대응을 전부 기록.
- 우리가 가진 것은 `fp_hash`(IP+UA 해시)와 타임스탬프, 그리고 **법정 접속기록**(봉인된 원본 IP + 접속시각 + 거친 요청 분류)이다. 접속기록은 `audit.access_log`에 3개월 쌓인다 ([D-030](./00-decisions.md)). 계정이 없어서 사람을 특정할 정보는 없다.

> **복호 함수는 앱에 없다** — 일부러 만들지 않았다(`src/lib/crypto.ts` `seal` 주석). 적법한 요청을 확인한 뒤 운영자가 별도로 복호한다. "임의 제공 금지"가 코드 구조로도 지켜지는 셈이다.
>
> **접속기록과 편지를 잇는 조인 키는 두지 않는다.** 그래서 "이 편지를 누가 썼는가"에는 답할 수 없다 — 답할 수 있는 것은 "이 시각에 이 IP가 접속했다"까지다. 요청이 오면 가진 것과 가지지 않은 것을 이 구분 그대로 전달한다. 있는데 안 준다고 오해받는 것도, 없는 것을 있다고 말하는 것도 둘 다 나쁘다.
>
> **"안 모았으니 줄 것이 없다"는 방어 논리가 아니다** ([D-030](./00-decisions.md)) — 보관의무가 적용되는 전제에서는 그것이 오히려 문제가 된다.

### 편지에 언급된 당사자

- 삭제 요청 경로를 안내한다 (§5).
- **발신자 정보는 제공하지 않는다.** 정책상 안 주는 게 아니라 **실제로 없다.** 이걸 명확히 말한다 — 있는데 안 준다고 오해하면 상황이 나빠진다.
- 반복 피해를 호소하면 §4로 처리한다.

### 언론

즉답하지 않는다. 질문을 받아 적고, 정리한 뒤 문서로 답한다.

## 7. 주간 점검 (30분)

1. [주간 리뷰 7개 지표](./06-analytics.md) 확인
2. 전환 트리거 5개 대조 (위협 모델 §7(비공개))
3. 등급 `medium` 편지 20건 샘플 검수 → 오탐이면 **개별 승격이 아니라 필터를 고친다**
4. 신고 `dismiss` 비율 확인 — 높으면 자동 비공개가 과하게 걸리는 것
5. **분류기 초안 판정 vs 내 최종 판정의 불일치율** — 높으면 초안을 믿으면 안 된다 (§2)
6. **재분류 워크플로가 실제로 돌았는지 확인** (Actions → `재분류 잡`) — GitHub Actions의 `schedule`은 지연·건너뜀이 있고 리포가 60일 비활성이면 멈춘다 ([05-api §1](./05-api.md)). 빠진 회차가 있으면 `workflow_dispatch`로 손으로 돌린다
7. **파기 워크플로가 실제로 돌았는지 확인** (Actions → `파기 잡`) — 6번과 같은 이유이고 **결과는 더 나쁘다.** 재분류가 안 돌면 편지가 `medium`에 머물 뿐이지만, 파기가 안 돌면 **보유기간 위반이 누적된다** ([D-031](./00-decisions.md)). 잡이 실패하면 스스로 `retention_healthy`를 끄고 작성을 막지만 **아예 안 돌면 실패도 안 한다** — 그 구멍을 이 점검이 메운다
8. **격리 30일 초과 건이 없는지 확인** (`/admin/queue` 맨 위 빨간 상자) — 있으면 그 이의 제기를 먼저 판정한다. 넘긴 상태 자체가 위반으로 읽힐 수 있다
9. 결정이 바뀌었으면 [결정 로그](./00-decisions.md)에 기록

3번은 **배치로 돌린다.** 제출 경로가 아니라 지연이 무관하고, 배치는 단가가 절반이다.

5번은 배치가 아니다 — 초안은 §2대로 신고가 접수될 때 이미 만들어져 `admin_actions`(`action='report_draft'`, `target_id`=신고 ID)에 저장돼 있고, 이 점검은 그 행과 최종 판정(`report_upheld`·`report_dismissed`)을 세는 집계뿐이라 모델 호출이 없다. `npm run weekly`가 주간 리뷰 일곱 개와 별개 블록으로 찍는다.

## 8. 운영자 자신에 대한 규칙

이 서비스의 운영은 **매일 이별 편지와 신고를 읽는 일**이다. 1인이라 교대가 없다. 이건 감상이 아니라 운영 리스크다.

- 큐를 30분 이상 연속으로 보지 않는다
- 심각 카테고리는 **판정에 필요한 만큼만 읽고 정독하지 않는다**
- 판정 기준은 §2 표를 따른다. 매번 새로 고민하면 소모가 누적되고 기준도 흔들린다
- 자리를 비울 때는 `writing_enabled = false` (§3). 큐가 쌓인 채 방치되는 것보다 낫다
- 하루 1시간을 넘기는 상태가 일주일 이상 지속되면, 그건 성실함으로 버틸 문제가 아니라 전환 트리거(위협 모델, 비공개)다
